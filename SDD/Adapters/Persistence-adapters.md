# Persistence Adapters Specification (Output Adapters)

## 1. Overview

Persistence Adapters reside in `aplication/nexusMarket/adapters/persistence/`. They implement the **Output Ports** defined in `domain/ports/out/` and consolidated in `SDD/domain/Output-ports.md`.

To guarantee technology independence and prevent persistence entities or ORM types from leaking into the Domain:

1. Persistence adapters do **not** use Domain Models as database entities or documents.
2. Every adapter works with its own **Persistence Entities / Documents (Repository DTOs)**, **Mappers** (Domain Model ↔ Entity/Document), and **Spring Data Repositories**.
3. The Domain never imports JPA, Spring Data, MongoDB, or Jakarta types; only the adapters do.

The stack is **Java / Spring Boot 4**, with **Spring Data JPA** over **MySQL** for every entity and **Spring Data MongoDB** for the audit trail, as in the banking reference.

**Source:** `SDD/domain/Output-ports.md`; `SDD/domain/services/operation-audit-services.md` (audit in MongoDB); the banking reference `SDD/Adapters/Persistence-adapters.md` and `SDD/Orchestrator-prompt.md` (phases 2A and 2B).

## 2. Architecture & Data Flow

```text
Domain Service (domain/services)
      |
      v  calls the Output Port interface
Output Port (domain/ports/out)
      ^
      |  implemented by
Persistence Adapter (adapters/persistence)
      |  1. maps Domain Model -> Entity / Document
      |  2. calls the Spring Data repository
      |  3. maps Entity / Document -> Domain Model, resolving its references
      v
Spring Data Repository (JPA / MongoDB)
      |
      v
MySQL  nexusmarket_db         MongoDB  nexusmarket_audit.audit_logs
```

## 3. Technology Stack Conventions

| Store    | Technology           | Entities / Documents                                  | Repositories                        |
| -------- | -------------------- | ----------------------------------------------------- | ----------------------------------- |
| MySQL    | Spring Data JPA      | `@Entity`, `@Table`, `@Id`, `@Column`, `@ElementCollection` | `JpaRepository<Entity, String>`   |
| MongoDB  | Spring Data MongoDB  | `@Document(collection = "audit_logs")`, `@Id`         | `MongoRepository<Document, String>` |

The connection is configured in `application.yaml` (`spring.datasource.*`, `spring.jpa.*`, `spring.mongodb.uri`), and the tables are generated by Hibernate (`ddl-auto: update`), as the orchestrator of the banking reference requires. The MongoDB collection is created with the first audit record.

## 5. Mapping Rules

These rules apply to every JPA entity and to the MongoDB document.

### 5.1 Catalogs are stored as their code

Every Value Object that inherits from `DomainCatalog` is stored as its `code` in a `String` column, never as an ordinal and never as a Java enum type in the entity. The mappers convert the code back through a single helper, `CatalogCodes.fromCode(Type.class, code)`, which searches the catalog's values by `getCode()`.

This keeps the database readable without the Java model and keeps the entities free of Domain types, as in the banking reference.

### 5.2 References to other aggregates are stored as identifiers

A Domain relationship to an entity that has its own lifecycle — `Order.buyer`, `Product.seller`, `Inventory.warehouse`, `OrderItem.sourceInventory`, and so on — is stored as the identifier of that entity (`buyer_id`, `seller_id`, `warehouse_id`, `source_inventory_id`). When reading, the adapter resolves the identifier back into the Domain Model through the corresponding Output Port, so the Domain always receives objects, never identifiers.

No JPA association (`@ManyToOne`, `@OneToMany` between aggregates) is used: aggregates are loaded explicitly by their own adapters, which keeps each table independent and each load predictable.

### 5.3 Parts of an aggregate are stored with it

Lines that belong to one parent and have no identity of their own in the Domain are stored as `@ElementCollection` embeddables of their parent:

| Domain line   | Parent table      | Collection table       | Columns                                                         |
| ------------- | ----------------- | ---------------------- | --------------------------------------------------------------- |
| `CartItem`    | `carts`           | `cart_items`           | `variant_id`, `quantity`                                        |
| `OrderItem`   | `orders`          | `order_items`          | `variant_id`, `quantity`, `unit_price`, `subtotal`, `source_inventory_id` |
| Shipment line | `shipments`       | `shipment_items`       | `variant_id`                                                    |
| `ReturnItem`  | `return_requests` | `return_items`         | `variant_id`, `quantity`, `refundable_amount`                   |
| Additional address | `users`      | `buyer_additional_addresses` | `address`, `position`                                     |

Within an order a line is identified by its variant, because the cart merges each variant into a single line (`order-services.md`). That is why shipment and return lines only store the `variant_id`: the adapter matches it to the order's own line when reading, so the Domain always works with the very same `OrderItem` objects.

`ProductVariant` is an entity with its own identifier and is stored in its own table, `product_variants`, owned by its product through a `product_id` join column.

### 5.4 Identifiers are assigned by the adapter

When `save` receives a Domain Model without identifier, the adapter assigns a random UUID before persisting it, as the banking reference does. Identifiers are therefore `VARCHAR(36)` strings in every table.

### 5.5 One table for every user

`User` is abstract with five specializations. They are stored in a single `users` table whose `role` column determines the specialization rebuilt by the mapper; the columns specific to buyers and sellers are empty for the other roles. This mirrors RG-02 — one role per user — and avoids joining five tables to authenticate a user.

### 5.6 Monetary amounts

`BigDecimal` amounts are stored as `DECIMAL(19,2)` next to their currency code, never without it (*Domain Model*, **Monetary Amounts Are Always Denominated**).

## 7. Reference Resolution

Each adapter rebuilds the references its port promises (`Output-ports.md`) by calling other Output Ports, so each aggregate is loaded by the adapter that owns it. There are two deliberate exceptions:

* **Users and warehouses** are resolved by `JpaReferenceResolver`, a small component that reads the `users` and `warehouses` tables through their mappers. `User` and `Warehouse` are abstract, so there is no instance to pass to their ports as a lookup key, and neither holds further references to resolve.
* **Shipments of an order** are read by `OrderJpaAdapter` directly from the `shipments` table. `ShipmentJpaAdapter` resolves orders through `OrderRepositoryPort`, so resolving shipments through `ShipmentRepositoryPort` in the other direction would make the two adapters depend on each other.

| Adapter                    | Resolves                                                                                   | Through                                               |
| -------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| `UserJpaAdapter`           | The specialization of each user                                                            | its own mapper                                        |
| `BuyerJpaAdapter`          | The buyer's active cart, as a reference                                                    | its own mapper                                        |
| `SellerJpaAdapter`         | The seller's warehouses                                                                    | the warehouses repository, owned by the seller itself |
| `WarehouseJpaAdapter`      | The owner of a seller warehouse                                                            | `JpaReferenceResolver`                                |
| `ProductJpaAdapter`        | The seller                                                                                 | `JpaReferenceResolver`                                |
| `InventoryJpaAdapter`      | The variant with its product and seller; the warehouse                                     | `ProductRepositoryPort`, `JpaReferenceResolver`       |
| `InventoryMovementJpaAdapter` | The performing user                                                                     | `JpaReferenceResolver`                                |
| `CartJpaAdapter`           | The buyer; each line's variant                                                             | `BuyerRepositoryPort`, `ProductRepositoryPort`        |
| `OrderJpaAdapter`          | The buyer; each line's variant and source inventory; payments, invoice, and shipments      | `BuyerRepositoryPort`, `ProductRepositoryPort`, `InventoryRepositoryPort`, `PaymentRepositoryPort`, `InvoiceRepositoryPort`, the shipments table, `JpaReferenceResolver` |
| `ShipmentJpaAdapter`       | The whole order, returning the shipment instance held by that order                        | `OrderRepositoryPort`, `JpaReferenceResolver`         |
| `ReturnRequestJpaAdapter`  | The order; each returned line, matched to the order's own line                             | `OrderRepositoryPort`                                 |
| `RefundJpaAdapter`         | The return request; the administrator who decided it                                       | `ReturnRequestRepositoryPort`, `JpaReferenceResolver` |
| `OperationJpaAdapter`      | The performing user                                                                        | `JpaReferenceResolver`                                |

`save` returns the same instance it received, now identified, rather than a copy rebuilt from the database: the services keep working on the object graph they built — for example Place Order, which saves the order and then reserves stock line by line on the same `OrderItem` objects.

`ShipmentJpaAdapter.findById` returns the shipment **instance held by its order**, not a separate copy: dispatching or delivering a shipment changes that object, and the order decides its own status from the same objects (`Order.isReadyForDelivery()`).

## 8. Code Pattern Example: `InventoryJpaAdapter`

### A. Entity (`InventoryJpaEntity.java`)

```java
@Entity
@Table(name = "inventories",
        uniqueConstraints = @UniqueConstraint(columnNames = {"variant_id", "warehouse_id"}))
@Getter
@Setter
@NoArgsConstructor
public class InventoryJpaEntity {

    @Id
    @Column(name = "inventory_id", length = 36)
    private String inventoryId;

    @Column(name = "variant_id", nullable = false, length = 36)
    private String variantId;

    @Column(name = "warehouse_id", nullable = false, length = 36)
    private String warehouseId;

    @Column(name = "available_quantity", nullable = false)
    private Integer availableQuantity;

    @Column(name = "reserved_quantity", nullable = false)
    private Integer reservedQuantity;

    /** InventoryStatus catalog code. */
    @Column(name = "inventory_status", nullable = false, length = 40)
    private String inventoryStatus;
}
```

### B. Mapper (`InventoryJpaMapper.java`)

```java
public static InventoryJpaEntity toEntity(Inventory domain) { ... codes and identifiers ... }

public static Inventory toDomain(InventoryJpaEntity entity, ProductVariant variant, Warehouse warehouse) {
    ... CatalogCodes.fromCode(InventoryStatus.class, entity.getInventoryStatus()) ...
}
```

### C. Repository (`SpringDataInventoryRepository.java`)

```java
public interface SpringDataInventoryRepository extends JpaRepository<InventoryJpaEntity, String> {

    Optional<InventoryJpaEntity> findByVariantIdAndWarehouseId(String variantId, String warehouseId);

    List<InventoryJpaEntity> findByVariantId(String variantId);

    boolean existsByVariantId(String variantId);
}
```

### D. Adapter (`InventoryJpaAdapter.java`)

```java
@Repository
@RequiredArgsConstructor
public class InventoryJpaAdapter implements InventoryRepositoryPort {

    private final SpringDataInventoryRepository inventoryRepository;
    private final ProductRepositoryPort productRepositoryPort;
    private final JpaReferenceResolver referenceResolver;

    @Override
    public Optional<Inventory> findById(Inventory inventory) {
        return inventoryRepository.findById(inventory.getIdentifier()).map(this::toDomain);
    }
    ...
}
```

## 9. MongoDB Audit Adapter

`AuditLogDocument` is stored in the `audit_logs` collection of `nexusmarket_audit`:

| Field                  | Content                                                       |
| ---------------------- | ------------------------------------------------------------- |
| `auditId`              | Identifier, assigned by the adapter.                          |
| `operationType`        | `OperationType` code.                                         |
| `operationDate`        | Moment of the operation.                                      |
| `performedByUserId`    | Identifier of the performing user.                            |
| `performedByFullName`  | Full name of the performing user, denormalized.               |
| `userRole`             | `SystemRole` code held at that moment.                        |
| `affectedEntityType`   | `AffectedEntityType` code.                                    |
| `affectedEntityId`     | Identifier of the affected entity.                            |
| `details`              | Operation-specific values, as plain data.                     |

The performer is denormalized so that the trail remains readable even if the user changes later; when reading, the mapper rebuilds a reference `User` of the specialization given by `userRole`, carrying its identifier and name.

The adapter offers no update and no delete, in line with `AuditLogRepositoryPort`.

## 10. Output Adapters Outside Persistence

Three Output Ports are not about storage. Their adapters live next to the persistence adapters because they are equally Output Adapters:

| Port                  | Adapter                                   | Implementation                                                                                   |
| --------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `PasswordServicePort` | `adapters/security/BCryptPasswordServiceAdapter` | Spring Security's `BCryptPasswordEncoder`.                                              |
| `JwtServicePort`      | `adapters/security/JwtServiceAdapter`     | JJWT, signing with the secret and expiration configured under `nexusmarket.jwt.*`. Claims: `userId`, `email`, `fullName`, `role`. |
| `PaymentGatewayPort`  | `adapters/payment/SimulatedPaymentGatewayAdapter` | Returns the outcome configured under `nexusmarket.payment.simulated-outcome` (`APPROVED` by default). |

**Inferred — simulated payment gateway.** The specification requires payments to be validated but names no financial provider, so the adapter simulates one. Replacing it with a real provider means writing a new adapter for the same port; the Domain does not change. This is the purpose of the port.

Validating incoming tokens and rebuilding the requesting `User` from them belong to the security and REST phase, as in the banking reference's orchestrator (phase 4).

---

## 11. Transactions

Each repository call runs in its own transaction for now. The business transaction that must span a whole service — for example Place Order, which saves the order, reserves several inventory records, and opens a new cart — is declared on the use-case adapters of the next phase (`@Transactional`), as established in `operation-audit-services.md`. The persistence adapters are written so that they can take part in such an outer transaction without changes.

---

## 12. Architectural Constraints

1. Persistence adapters implement Output Ports and live outside the Domain.
2. Entities and documents are persistence DTOs; Domain Models are never annotated with JPA or MongoDB annotations.
3. Catalogs are stored as their codes; references to other aggregates, as identifiers.
4. Lines without identity are stored as element collections of their parent.
5. Adapters resolve references through Output Ports, except users and warehouses (`JpaReferenceResolver`) and an order's shipments, for the reasons given in section 7.
6. Identifiers are UUIDs assigned by the adapter on first save.
7. Only `AuditLog` is stored in MongoDB.
8. No adapter deletes records; immutable records are never updated.
9. The Domain never imports a persistence, driver, or security library type.
